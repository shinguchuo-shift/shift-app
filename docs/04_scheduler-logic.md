# 04 自動作成とチェックのロジック

正解はデモ `reference/shift-demo.html` の `generate()` と `checks()`。`web/js/scheduler.js` に **DOM に依存しない純粋な関数** として移植し、`test/scheduler.test.mjs` でテストする。

## 単位のルール（最重要・先に読む）

**scheduler の内部は「スロット番号」で計算する。分で計算しない。**

- `slot` = 営業開始からの通し番号（0, 1, 2 …）。`grid_min` が60なら1スロット＝1時間
- 分⇔スロットの変換は **入口と出口だけ**でやる（`minToSlot(min)` / `slotToMin(slot)`）
- スコア式の `len` も**スロット数**。分（180〜480）を入れてはいけない

なぜこれを最初に書くか：デモの点数式は `hit`（スロット数）と `len`（時間数）が混ざっている。1時間刻みだから偶然一致しているだけで、`CLAUDE.md` の「時間は分で持つ」に素直に従って `len=180` を入れると
`-0.6 × (180 - 3) = -106` となり、**全候補がマイナス点になって誰も配置されない**。エラーも出ずに空のシフトが返るので、気づきにくい。

`grid_min` は **60 固定**（`06` #2 で「30分単位の人はいない」と確定）。30分対応は「やらない」に移したので、係数の grid 正規化は不要。将来やるときはこの節から読み直すこと。

## 入力と出力

```js
// 入力
{
  days: [{ date: "2026-11-02", dow: 0, dayType: "weekday" }, ...],   // 7日
  slots: [600, 660, ..., 1380],          // grid_min 刻みの開始時刻（営業時間内）
  grid: 60,
  staff: [{ id, name, capMin, leader, closer, pos: { reg:2, ... }, ng: ["s04"] }],
  positions: [{ key:"reg", side:"hall" }, ...],
  requests: { [staffId]: { [date]: { start, end } } },   // 出られる時間。中抜けなし（06 #9）なので1日1枠で確定
  demand: { weekday: { hall:[...], kitchen:[...] }, weekend: {...} },  // slots と同じ長さ
  peaks: [[660,840],[1020,1200]], weekendPeakBoost: 1,
  rules: { leader:true, peak3:true, close:true, ng:true, rookie:true },
  minLen: 180, maxLen: 480, closeMin: 1440
}
// 出力
generate(input)  → [{ date, staffId, side, start, end }]
checks(input, shifts, date) → [{ kind:"不足"|"責任者"|"ピーク"|"締め"|"NG"|"教育中", level:"error"|"warn", message }]
```

## 補助の定義

- `level(staff, side)` = その side のポジションのレベルの最大値（0〜3）
- staff が入れる side = level が 1 以上の side
- `need(day, side, slot)` = demand[dayType][side][i] ＋（土日 かつ slot がピーク内なら weekendPeakBoost）

## 自動作成（貪欲法）

1. 日の処理順：**土 → 日 → 金 → 月 → 火 → 水 → 木**（忙しい日を先に埋め、上限時間を先に使う）
2. 各スタッフの週の使用時間 `used` を 0 で開始
3. 各日について、配置数 `c[side][slot]`、責任者数 `lead[slot]`、レベル3の数 `v3[side][slot]`、締め要員数 `closer` を 0 で開始。1日1人1回まで
4. 候補を全部試して一番点数の高いものを1つ配置、を点数が 0 以下になるまで繰り返す
   - 候補 = （まだその日に入っていない人）×（入れる side）×（希望時間内の開始 a）×（長さ minLen〜min(maxLen, 希望の終わりまで, 残り上限)）
   - 残り上限 < minLen の人は候補にしない
   - rules.ng が ON なら、NG相手と時間が重なる候補は除外
5. 点数（候補の各 slot について数える。**すべてスロット数**）
   - `hit` 人手が必要数に足りていない slot の数
   - `lh` 責任者がいない slot を、この人（leader）が埋める数（rules.leader）。**`need > 0` の slot に限る**
   - `ph` ピーク内でその side のレベル3がいない slot を、この人（レベル3）が埋める数（rules.peak3）。`need > 0` の slot に限る
   - `alone` この人がレベル1で、その side のレベル3がいない slot の数（rules.rookie）
   - `ch` 終了＝閉店 かつ この人が closer かつ まだ締め要員がいない なら 1（rules.close）
   - `useful` 上のどれかで役に立つ slot の数。0 なら候補にしない
   - `len` この候補の長さ（**スロット数**。分ではない）
   - `usedH` この人がその週までに使った時間（**時間単位**）
   - **点数 = hit + 1.2·lh + 0.8·ph + 1.5·ch − 0.6·(len − useful) − 0.4·alone − usedH/200**
6. 配置したら c / lead / v3 / closer / used を更新

`lh` の `need > 0` 条件はデモにはない（デモは10〜24時すべて need≧1 なので表に出ない）。必要人数0の時間帯を入れると **客がいない時間に責任者を置くためだけに人が入る**ので、移植時に足すこと。

係数はデモで調整した仮の値。店長の手直しが多い所を見て調整する。調整したらテストの期待値も更新する。
**係数は1箇所にまとめる**：`WEIGHTS = { hit:1, leader:1.2, peak3:0.8, close:1.5, waste:0.6, rookie:0.4, usedDiv:200 }` のようにオブジェクトへ外出しし、各行に「大きくすると何が起きるか」をコメントで1行書く。後で触るのはここだけ、という状態にしておく。

### 既知のクセ（Phase 6 で調整する候補）

**希望時間を細切れに使う。** 候補は希望内の任意の開始・任意の長さを全部試すので、「10〜18時で出られます」に対して「14〜17時」が割り当たりうる。`−0.6·(len − useful)` が短い勤務を好む方向に働くため実際そうなる。手直しが多いようなら「希望の開始時刻に一致したらボーナス」を足せるフックを用意しておく。

## チェック（日ごと）

| kind | 条件 | level |
|---|---|---|
| 不足 | 各 slot の（必要数 − 配置数）の合計 > 0 | error |
| 責任者 | rules.leader：責任者が 0 人の slot がある（連続する時間をまとめて「10〜12時」と表示） | error |
| ピーク | rules.peak3：ピーク内の slot で side ごとにレベル3が 0 人 | error |
| 締め | rules.close：閉店時刻に終わる closer がいない | error |
| NG | rules.ng：NG同士の時間が重なっている | error |
| 教育中 | rules.rookie：レベル1の人の勤務中に同じ side のレベル3がいない slot | warn |

**level は Rules シートの `level` 列から読む**（`02` 参照）。上の表はその初期値。`06` #5 で店長に「絶対／できれば」を聞いたら、コードではなくシートを直す。

「不足」の表示は `スロット数 × grid_min / 60` を計算して「人×h」と出す。デモは `grid=60` 前提でスロット数をそのまま「人×h」と表示しているので、移植時に直すこと。

手直しのたびに全チェックを再計算する（20人×7日なら一瞬で終わる。実測で `generate()` が12ms、`checks()` はさらに軽い）。

## テストで確認すること（最低限）

- デモと同じサンプルデータ（`reference/shift-demo.html` の `sampleReq` / `sampleSkills`、seed 固定の乱数）で、デモと同じ結果になる
- どの人も週の上限を超えない、希望時間の外に入らない、1日1回まで
- rules.ng が ON なら NG 同士が重ならない
- ルールを全部 OFF にしたら、不足以外のチェックが出ない
- 必要人数を全部 0 にしたら誰も入らない
- **誰も配置されない結果を「正常」として通さない**：サンプルデータで配置数が0なら必ず失敗するテストを1本入れる（上の「単位のルール」を踏み外したときに気づくための保険）

### 移植は2段階でやる

1. **まずデモと完全一致させる**。時間単位のまま（`minLen=3`, `maxLen=8`）移植し、デモと同じシフトが出るテストを通す。ここを固定点にする
2. **そのあとスロット単位へ変える**。1のテストが通り続けることを確認しながらリファクタする

一気にやると、単位の取り違えで結果が変わったのか、リファクタのミスなのかが切り分けられなくなる。
